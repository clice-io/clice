# 源码概览

本文档介绍 clice 源码中各模块的职责与定位，帮助读者建立对整个项目结构的整体认知。关于每个模块的详细设计，请参阅对应的专题文档。

## 项目愿景

clice 是一个全新的 C++ 语言服务器，从架构层面重新设计，旨在解决以往 C++ 语言服务器长期存在的问题。主要特点：

- **编译上下文**：clice 是首个将编译上下文作为正式概念引入的语言服务器。编译、索引和查询的每个步骤都会明确区分当前的编译上下文，用户可以查询和切换这些上下文。详见 [编译上下文](compilation-context.md)。

- **多进程架构**：master + worker 进程模型将 Clang 的内存泄漏和崩溃隔离开来，同时支持感知优先级的调度和实时内存监控。详见 [多进程架构](multi-process.md)。

- **协程异步模型**：基于 C++20 协程和 kotatsu 库，取代传统的回调式异步，使业务逻辑更清晰。

- **统一编译调度**：每个高开销的构建产物——Preamble PCH、C++20 模块 PCM、文档 AST、为索引或 lint 进行的一次翻译单元编译——都是统一编译任务图中的一个节点，支持构建共享、实时协作式取消和感知依赖关系的失效处理。详见 [编译任务图](task-graph.md)。

## 模块概览

### `src/support/` — 基础工具库

供其他所有模块共享的通用工具和基础设施。

- `FuzzyMatcher`：用于代码补全和符号搜索的 Token 感知模糊匹配。
- Markup：卡片或查询答案渲染所用的 Markdown 或纯文本。
- `FailureRecord`：失败操作留下的记录——连续失败了几次、何时失败、为何失败——以及该操作何时再次运行的策略：失败几次后停止、冷却时间、输入变化或保存是否会让它重试。
- 日志、文件系统抽象、字符串工具等。

### `src/vfs/` — 文件标识与版本

- `FileTable`：将文件路径映射为全系统使用的稳定 `Fid` 标识，并管理据此得到的各文件共享信息——每个文件在磁盘上最近一次的观察记录、内容版本和目录列表。同一个文件无论路径怎么写，都只有一个 `Fid`：识别文件时用的是操作系统给它的名字（穿透符号链接；在 Windows 上还会穿透大小写差异、junction 和 subst 盘符），展示给用户时则用用户熟悉的名字——已打开文档所用的名字，否则是它在用户所打开工作区文件夹下的路径，从不使用 include 查找时找到它所用的写法。两层时效性检查（先走 stat 快速路径，再计算内容哈希）集中实现在此处，供所有使用方共享：PCH 验证、索引过期判断和磁盘轮询。无论由谁查看，只要某次查看发现的内容与上一次不同，就会报告为一次变化。
- `CacheStore`：面向文件型构建产物（PCH/PCM 等）的磁盘制品存储——成对原子提交、命名空间配额、LRU 淘汰和崩溃恢复。

### `src/settings/` — 设置

- `Settings`：加载并合并 `clice.toml` 与 LSP `initializationOptions`，带位置的错误与未知键警告，用于生成配置文档的 JSON schema，以及选择构建配置。
- `Rules`：某一构建配置下 `clice.toml` 的规则，也是唯一知道规则优先级的地方：一个文件匹配哪些规则，这些规则如何编辑它的命令，它是否参与索引、lint 和格式化，哪条默认命令涵盖它，以及它按什么顺序从哪些数据库取得命令。

### `src/command/` — 编译命令处理

从编译数据库（CDB）读取的命令是构建系统生成的原始命令，不能直接交给 Clang 前端——它们可能包含仅用于代码生成的选项、缺少系统头文件搜索路径，或者包含与语言服务器无关的参数。本模块只需解析每条命令一次，即可将其转换为供系统其余部分使用的结构化形式。

- `CommandTable`：clice 知道的每一条命令，各自只解析一次，形成由稳定 `CommandID` 标识的、经过驻留和分类的参数结构，并附带由一条命令推导出的内容：输入语言、写出和读取的预编译头文件、命令哈希，以及 driver 层面的渲染结果。
- `CompilationDatabase`：加载和重新加载 `compile_commands.json` 文件，并比对其新旧差异；文件中的条目经规范化（`Normalizer`）后存入 `CommandTable`；规则所做的编辑应用在条目的命令之上（`apply_edits`）。
- `Toolchain`：查询系统编译器以获取隐式编译参数（例如系统头文件搜索路径），并采用两层缓存——按 driver 调用形式缓存查询结果，按输入类型缓存合成的选项集——还负责渲染 `-cc1` 命令行；每种编译器的询问方式（GCC 风格、cl、nvcc、clang 自身的 driver）位于 `src/command/toolchains/` 下。
- `SearchConfig`：头文件搜索路径的四层模型（Quoted / Angled / System / After），与 Clang 内部的搜索逻辑一致。

详见 [编译命令解析](command-resolve.md)。

### `src/compile/` — 编译抽象

封装 Clang 编译器，将 Clang API 抽象为安全、统一的编译接口。这一层是纯粹的编译抽象，不包含任何服务器逻辑。

- `CompilationUnit`：一次编译的 AST、Clang 运行时报告的内容（诊断、预处理器指令、Token、依赖），以及读取它们的辅助函数，例如源位置映射。它由 `compile()` 返回，是 `src/feature/` 和 `src/index/` 的主要输入。
- `CompilationParams`：描述单次编译：编译类型（Preprocess / Preamble / ModuleInterface / Content / Whole / Completion）、输入（编译命令、从内存提供的文件、要加载的 PCH 和 PCM），以及在解析之上额外运行的内容，例如 clang-tidy。
- 在编译期间收集诊断信息和 clang-tidy 结果。
- 上层基于 AST 推导出的内容（例如语义映射）在首次使用时才构建，之后随编译单元一起保存（`CompilationUnit::get`）。

### `src/syntax/` — 轻量级语法处理

无需完整 AST 的语法级处理。在编译前运行，可快速获取文件的结构信息和依赖关系。

- `Lexer` 与词法扫描：`Lexer` 是基于 Clang 原始词法分析器构建的 Token 级工具，负责标记指令行、指令关键字和头文件名。词法扫描对一个文件只做一次词法分析，得出它的 Token、注释和指令行（连同每条指令行外层的条件块）、头文件保护（include guard）和模块声明；凡由打开文件的编译单元作答的功能，都共用该编译单元缓存的这一份扫描结果。二者都不运行预处理器。
- `DependencyGraph`：全局 include/模块依赖图，支持正向查询、反向查询、宿主源文件搜索、include 链查找等。
- 依赖扫描：封装 Clang 的 `DependencyDirectivesScanner`，快速提取 include 和模块依赖
- `IncludeResolver`：根据搜索路径配置将 include 路径解析为实际文件
- 头文件上下文：构建前缀/后缀文件，使头文件能够在其宿主文件的预处理器状态下编译
- 文档注释：在文件文本中找出为声明撰写的注释，编译单元和索引的找法相同；再按 Doxygen 和 Markdown 的规则读取其中的命令、参数、返回值和 `@copydoc`，得到统一的结构化形式，供悬停和 `clice query` 渲染

详见 [依赖扫描](dependency-scanning.md)。

### `src/semantic/` — 语义分析

提供 Clang 原生 API 之外、基于编译单元 AST 的语义分析能力。

- `Semantics`：统一语义映射——每次编译仅遍历一次 AST，记录所有相关节点及其 Token 归属；选择、各项功能和索引生成都是对该映射的纯查询，而无须分别遍历 AST
- `EntityTable`：声明的标识；编译器会合并的声明，在不同翻译单元中得到相同的标识
- `TemplateResolver`：通过伪实例化解析依赖名，使语义分析能够透视模板上下文。详见 [模板解析器](template-resolver.md)。
- `SymbolKind` / `RelationKind`：细粒度的符号种类和关系类型

### `src/index/` — 符号索引

支持跨翻译单元查询的符号索引系统。层次结构如下：

- `TUIndex`：单次编译产出的索引条目，从语义映射投影而来
- `ProjectIndex`：全局层——包含外部可见符号，以及翻译单元与其所贡献文件之间的对应记录——内存中与磁盘上的索引由这同一个类型承担：它合并各翻译单元的索引，判断它们是否过期，将自己的改动保存到索引数据库，加载时再将其读回
- `Shard`：以文件为单位的存储单元。每个以不同方式预处理该文件的编译上下文都会产生一个变体，这些变体根据其编码后条目的内容标识去重；文件局部名称保存在分片本身，只有外部名称会进入 `ProjectIndex`
- `BlobDatabase`：持久化后端——所有索引 blob 都存放在单个 LMDB 数据库中
- `IndexQuery`：对所有索引来源——项目索引、按文件划分的分片，以及持有者为一次读取以普通数据交给它的打开文档的索引——执行只读查询，并统一仲裁数据时效性；以领域值作答，再由各传输层映射到各自的协议；查询还可以向其他项目的视图询问同一个实体，每个视图只为它服务的文件作答

详见 [符号索引](symbol-index.md)。

### `src/feature/` — LSP 功能实现

LSP 功能的具体实现。每个功能根据传给它的输入——`CompilationUnit`、索引（`IndexQuery`）、文档的文本——决定用户看到什么：有哪些条目、条目的文本与编辑，以及它们的协议形式。这一层是纯粹的计算层，不涉及网络通信、状态管理或进程调度。

包括：代码补全、悬停信息、签名帮助、语义高亮、内联提示、文档符号、文档链接、折叠范围、格式化、诊断等。

> `feature/` 决定每个请求的结果；服务器把每个请求路由到此刻能作答的来源，收集该功能的输入，调用它并回复。跨文件代码导航功能（转到定义、查找引用等）由索引（`IndexQuery`）作答。部分功能涉及多阶段处理——例如，代码补全中的 include 路径补全无需完整编译即可在语法层处理。

### `src/worker/` — Worker 进程

- `WorkerPool`：管理 worker 进程的生命周期与调度——在崩溃预算约束下启动、监控和重新拉起进程，并在冷却后恢复；将每次 worker 退出归因于导致它的请求；为每个请求设定截止时间；基于文档亲和性安排有状态任务；通过优先级队列和感知前台负载的容量管理分发无状态任务
- `StatefulWorker`：持有文档 AST 并响应查询请求
- 无状态 worker 执行一次性任务（PCH/PCM 构建、代码补全、格式化、索引任务）

### `src/project/` — 项目及其构建

一个项目由一组编译数据库和一个缓存目录描述：它包括从磁盘文件推导出、独立于编辑器的状态，以及它在这份状态之上运行的构建——它的 PCH、模块和索引。命令行只运行一个项目。服务器为每个工作区文件夹运行一个项目；对于在这些文件夹之外打开、且所在目录或某个上级目录中含有 `clice.toml` 或 `compile_commands.json` 的文件，也会再为其运行一个项目，并把每个文件交给负责编译它的项目。带有自己配置的子目录自成一个项目：上层项目不加载那里的任何数据库，也不把其中的文件当作自己的文件，除非上层项目自己的数据库列出了它们。

- `Project`：以磁盘状态为准的聚合体——包含配置、它的规则（`Rules`）、编译数据库、成员、依赖图、PCH 与 PCM 条目、持久化索引以及对它的查询（`IndexQuery` 及其时效性判断），还有它的构建所运行的任务图，以及它的持有者交给它的事件循环和 worker 池。它是一个类，各项操作都是它的成员，按主题拆分到多个文件中（`command/`、`graph/`、`background/`）。核心不变量：打开文件中未保存的缓冲区内容绝不会改变 `Project` 对磁盘的描述；它唯一从缓冲区得知的内容——头文件能否单独编译——会记录在该文本的版本之下，以磁盘为准的读取方会忽略这条记录，直到磁盘内容变成该版本为止
- 打开（`Project::open`），所有入口都用同一种方式，按固定顺序进行：取当前配置下的规则，打开缓存存储和索引数据库，读取索引记得的数据库和临时成员，加载构建及其依赖图，最后让保存的索引与构建对齐
- 发现：项目的编译数据库在哪里、如何盯着它们——改写后连续两次看到同样的内容才重新加载、发现的数据库是否存在决定它的排名、数据库可能出现的位置一直盯到它出现为止——一个文件的项目以哪个目录为根，以及哪些子目录自成项目
- 成员：构建要编译的内容——规则之下每个文件的数据库条目、规则的默认命令所涵盖的源文件，以及临时成员（用户打开或保存过、但没有任何数据库列出的源文件）——以及它们编译时采用的命令
- 变化：项目的输入（磁盘上的文件、构建的命令）变化后哪些东西失效——重新扫描包含图和模块图，读过该文件的 PCM 和翻译单元过时，没打开的翻译单元排进重建索引的队列，消失的文件被忘掉。项目从不调用它的持有者：服务器把打开的文档和它们的编译读过的文件交给项目，项目告诉服务器其中哪些过时了
- 命令解析：仅依据项目得出文件编译时采用的编译命令：先按顺序从六级中选出——用户选择的宿主、文件自身的命令、排名第一的宿主、规则的默认命令、从附近翻译单元借用的命令、clice 自己的兜底命令——每一种都是一个候选，并写明它是哪个文件的命令；再连同头文件所需的包含方上下文一起渲染；此外还有翻译单元命令的标识——套用规则之后它实际编译用的命令，项目根写作 `${workspace}`，所以换个位置检出也不变——它的索引、包含树、自包含检查和头文件上下文都以此为键
- `Hosting`：clice 对在某个翻译单元的上下文中编译的头文件所掌握的信息，编辑器和 `clice inspect` 读取的是同一份：宿主的包含树、每个头文件能否单独编译（与 PCH 和 PCM 记录一同保存）、合成的包含方上下文，以及构建之外的文件能借用的命令
- 上下文：一个文件可以在哪些上下文中编译——它自己的命令，以及它可以借用其命令来编译的宿主——用户的选择是否仍然成立，以及选择保存时的格式
- `TaskGraph`：共享构建图。每个计算开销较大的产物都是一个节点——Preamble PCH、模块的 PCM、打开文档的 AST、为索引或 lint 进行的一次翻译单元编译；等待节点的一方携带构建它的方式；对同一节点的并发请求会汇入同一次尝试，避免重复工作；等待者到达干净节点时会检查该节点的产物；取消采用协作式机制；图中的边会按依赖关系驱动失效处理
- PCH 与模块：构建 Preamble PCH（以内容为键）与 C++20 模块 PCM（包含导入边和提供方跟踪），每个条目都保存自己的产物和上一次构建的失败；以及两者共用的部分（`Precompiled`）：一次构建的键与 blob、对照缓存构建所记录的输入进行的检查、拒绝失败或导致 worker 崩溃的构建，直到已知它读取过的文件发生变化（读取方一再读取失败的 PCH 则暂停一段时间），以及把构建交给无状态 worker
- 翻译单元：在无状态 worker 上为索引或 lint 编译一个翻译单元，由后台索引和 `clice lint` 共用
- `BackgroundIndex`：由项目的持有者启动——启用索引时由服务器启动，`clice index` 一开始就启动，`clice lint --index` 在自己的 lint 完成之后启动——它在待重建索引的队列（`ReindexQueue`，记录每个翻译单元需要重建索引的原因）上一轮轮运行，只接纳构建中的翻译单元，把它们交给无状态 worker 处理，只占用前台留下的容量，并合并返回的结果；由打开文档的编译来建索引的翻译单元在文档关闭前交给该文档，一次运行的跳过函数体诊断随该文件上一次尝试的记录保存；尝试结束和索引变化以信号告知，由持有者订阅
- `SavedMembers`：上次保存索引时每个文件被哪些数据库列出，以及临时成员。加载时，没有服务器运行期间命令发生变化的翻译单元会重建索引，因为它的索引记录了构建它所用的命令；不再被任何数据库列出的翻译单元，其索引会被丢弃——前提是列出过它的每个数据库都加载成功，加载失败的数据库所列的单元继续提供服务
- 保存与加载：一次事务写入索引的改动，连同数据库随索引一并存放的内容——成员、PCH 与 PCM 记录、编辑器的上下文选择——加载时再将它们读回；关停（`Project::shutdown`）时停止后台索引，让任务图中的尝试收尾，最后保存一次，并关闭缓存存储
- `Memo`：按请求记住的结果，附带每个结果读取过的文件记录，查找时会核对这些文件：宿主的包含树、自包含检查的结果，以及合成的头文件上下文

### `src/server/` — 服务器运行时

语言服务器的核心运行时，负责将上述各层组装成可运行的服务：设计中的每个边界对应一个类，较大的类各占一个目录，其工作再按文件拆分。

- `MasterServer`（`master/`）：进程本身。持有文件表、worker 池和所服务的各个项目，并持有编辑器的状态，整个进程只有一份：打开的文档——每个文档所属的项目，以及它的文件以第二个名字打开的文档——和用户的上下文选择。它把每个打开的文件交给负责编译它的项目，并通过更换所属项目把文档移到另一个项目；生命周期、轮询和关停也由它负责
- `Session`：一个打开的文档——它的文本、版本和代次——以及在它上面崩溃过的工作：某类工作在该文档上导致 worker 崩溃后，这类工作会暂停，直到文档发生变化（有间隔、有次数上限）或被保存。这些记录与文档的打开期同生共死
- `LSPClient`（`client/`）：与编辑器的连接：握手与客户端能力，交给 `MasterServer` 处理的文档通知，所有语言功能请求——每个只在它的处理函数中写一次，并统一经过一次服务器生命周期检查——clice 自己的请求，诊断推送与唯一的刷新函数——当更好的答案取代了索引给出的答案时请求客户端刷新，连接在作答时记下哪些答案来自索引——进度，以及测试钩子
- `ServedProject`（`served_project/`）：一个被服务的项目：它的项目、属于它的打开文档，以及它为这些文档推导出的一切——编译它们，以及它们的诊断显示什么；判断此刻由谁回答针对它们的请求（worker 的 AST、PCH 中缓存的 Preamble 产物或索引，依据就绪状态和文档是否编译：有最新 AST 时由 AST 回答，否则立即由根据索引算出的结果回答，请求自己说明需要什么——只要 AST、对整个缓冲区做词法分析、等待该文件正在进行的那次索引），并向 worker 发出请求，每次派发都经过该文档崩溃记录的准入检查，若客户端已修改对应的缓冲区则回复 `ContentModified`；项目的变化对打开文档意味着什么；在上下文选择下确定打开文档的编译命令；以及把打开文档按索引读取所需的样子交出去。在 `readonly = auto` 下，文档不编译——它的读取请求只由索引回答——直到一次编辑意图让它开始编译，在 `readonly = on` 下则始终不编译；编译始终按需进行，由请求而非生命周期事件触发
- 协议：LSP 扩展类型，以及 `clice index` 和 `clice query --fresh` 用来请求运行中的服务器建立索引的控制通道——服务器在持有项目索引写入锁期间开启的回环监听端口，地址记录在锁旁边，供命令行工具查找

详见 [多进程架构](multi-process.md)。

### `src/driver/` — 子命令

`clice` 二进制程序的入口点：`serve`（LSP 服务器）、`worker`、`index`（批量索引）、`lint`（批量 clang-tidy）、`inspect`、`format`、`query`、`refactor` 和 `analyze`。`index` 和 `lint` 各自运行一个项目，带着自己的 worker 池，不依赖编辑器。

## 模块间关系

数据流大致如下：

```text
command (structured compile commands)
    ↓
project (task graph: PCH / PCM / AST / unit nodes) ──→ worker (processes)
    ↓ products
compile (drives Clang compilation)
    ↓
semantic (semantic map) ──→ index (TUIndex / shards / ProjectIndex)
    ↓
feature (produces LSP responses)

The server layer assembles all of the above via sessions, routing,
invalidation, and transports into a runnable service.
```

`support`、`vfs`、`config` 和 `syntax` 是多个模块共享的横切层。
