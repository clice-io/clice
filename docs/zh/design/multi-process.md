# 多进程架构

## 背景

C++ 语言服务器面临一个独特的工程挑战：它依赖 Clang 解析代码，而 Clang 在处理不完整或不合法的代码时，有许多代码路径未经过充分测试。编辑器中的代码几乎总是不完整的——缺少分号、括号不匹配、模板实例化中断——这些场景都不是 Clang 最初设计要稳健处理的。这会导致两个严重问题：

**内存泄漏与膨胀**：Clang 的设计假定编译是短生命周期的一次性操作。编译器进程分配内存、完成编译后退出，操作系统会回收所有资源。但语言服务器是长期运行的进程——用户每次编辑都会触发重新编译，而 Clang 内部累积的内存无法得到有效回收。在 clangd 社区中，用户经常报告服务器运行数小时后内存占用达到 10 GB 以上，最终被系统的 OOM killer 终止。典型场景包括：模板与宏的组合导致后台索引耗尽 16 GB 内存；合法代码（如大型数组声明 `arr[50][6000000]`）因常量初始化检查而导致 OOM。

**崩溃**：不完整的代码会触发 Clang 内部的各种断言失败和空指针解引用。clangd 的问题跟踪器中有大量报告涉及模板实例化崩溃、枚举声明段错误、catch 子句中的命名空间损坏等场景。由于 clangd 采用单进程架构，任何一次崩溃都会终止整个语言服务器，导致用户丢失所有编辑状态——即使崩溃只与一个文件有关。

**优先级倒置**：在单进程 / 单线程架构中，后台索引和前台交互请求（悬停、代码补全等）会争用同一个线程。当后台索引正在处理大型文件时，用户的悬停请求可能需要等待数秒才能得到响应。即使使用线程池，也很难控制线程之间的优先级——操作系统的线程调度器并不理解“用户正在等待悬停结果”这类语义。

## 设计方案

### 核心思想

clice 通过多进程架构解决上述问题：每个编译任务都在独立的工作进程中运行，主进程只负责状态管理和请求路由。工作进程的崩溃或内存泄漏被隔离在进程边界内，既不会影响主进程，也不会影响其他工作进程。

### 进程模型

```text
Master Process (MasterServer)
├── Event loop (kota)
├── LSP / control protocol handling
├── State management (workspace, sessions, invalidation)
├── Compile scheduling (task graph: PCH and PCM builders, AST and TU-run families)
├── Background indexing (project index + pump)
│
├── Stateful Worker Processes × N
│   ├── SF-0: holds AST, serves queries
│   ├── SF-1: holds AST, serves queries
│   └── ...
│
└── Stateless Worker Processes × M
    ├── SL-0: executes one-shot tasks
    ├── SL-1: executes one-shot tasks
    └── ...
```

所有工作进程都通过 stdin/stdout 管道与主进程通信，并使用 bincode 进行序列化（这是一种基于 kotatsu 的 BincodePeer 的高效二进制格式）。每个工作进程的 stderr 都会重定向到独立的日志文件，以便单独调试。

### 主进程的角色

主进程是整个系统的协调者，运行单线程事件循环。它不执行任何 CPU 密集型编译工作——所有编译都交由工作进程完成。主进程负责：

- 接收和路由 LSP / 控制请求
- 管理全局状态（项目、Session 映射）
- 调度编译任务和后台索引
- 监控工作进程的运行状况
- 处理文件变更通知和级联更新

单线程设计意味着主进程无需加锁——所有状态修改都在事件循环中串行执行。这大幅降低了状态管理的复杂度。

### 为什么需要两类工作进程

语言服务器的编译任务天然分为两类，这两类任务的特性不同，因此需要采用不同的调度策略：

**需要持有状态的任务**：用户打开文件后，会反复查询其悬停信息、语义高亮、符号大纲等。这些查询都基于同一个 AST。如果每次查询都触发重新编译，延迟将难以接受（一次完整编译可能需要数秒）。因此，必须将编译后的 AST 保留在内存中，供后续查询复用。这类任务要求具备**文件亲和性（file affinity）**——每个文件都固定绑定到一个进程。

**一次性任务**：PCH 构建、PCM 构建、后台索引、代码补全、签名帮助、格式化等都是一次性的——执行完毕后不需要保留状态。这类任务需要**负载均衡和优先级调度**——任何可用的工作进程都可以执行，但用户交互任务应该优先于后台任务。

将它们分配给两类工作进程，可以让每类工作进程采用最合适的调度策略。

## 有状态工作进程

有状态工作进程的核心职责是持有已编译的 AST 并处理查询请求。

### 文件亲和性路由

每个打开的文件通过 path_id 绑定到一个有状态工作进程。这个绑定关系存储在主进程的路由表中。当该文件的查询请求到达时，主进程根据路由表将请求发送到对应的工作进程。

新文件采用**最低负载**分配策略——选择当前持有文档最少的工作进程。这可以确保文档均匀分布在各工作进程之间。

### 编译与查询流程

1. 主进程发送 CompileParams（源码文本、编译参数、PCH/PCM 路径等）
2. 工作进程编译 AST，并将其缓存在内存中的 DocumentEntry 中
3. 后续的功能请求（悬停、语义 Token、文档符号等）复用缓存的 AST
4. 当文件内容发生变化（didChange）时，主进程发送 DocumentUpdate 通知
5. 下次收到编译请求时，工作进程使用新内容重新编译 AST

每个文档的请求都通过该文档专属的互斥锁串行执行，确保不会在同一文档上并发执行编译和查询。

### 文档淘汰

当工作进程持有的文档数量超过限制时，会通过 LRU 策略淘汰最久未使用的空闲文档，释放其 AST 占用的内存。有编译或查询正在进行的文档绝不会被淘汰——此时宁可让文档数量短暂超出限制——因此，当一次涌入的文档多于限制时，系统会逐渐稳定下来，而不会淘汰那些随后又得从头开始的编译。工作进程会向主进程发送淘汰通知。后续对该文档的请求会触发工作进程的重新分配和重新编译。

## 无状态工作进程

无状态工作进程执行一次性编译任务，并采用考虑优先级的调度策略。

### 两级优先级队列

- **高优先级**：用户请求正在等待其完成的工作——交互式构建（代码补全、签名帮助）、格式化，以及前台请求所依赖的 PCH/PCM 构建。
- **低优先级**：后台索引任务，可以推迟执行而不影响用户体验。

优先级是调度的属性，而不是任务类型的属性：同一个 PCH 构建，在用户请求等待其完成时以高优先级调度，由后台索引产生时则以低优先级调度。

高优先级任务始终优先获取工作进程资源。低优先级任务受并发限制——同时运行的低优先级任务数量有上限，确保始终有工作进程可用于处理高优先级请求。后台索引任务还会运行在调度优先级较低的线程上，该线程随任务一同结束，从而减少其 CPU 占用对系统中其他进程（包括编辑器本身）的影响。

### 动态并发控制

低优先级任务的并发上限根据系统状态动态调整：

**前台感知预算**：用户空闲时，后台工作最多占用配置数量的无状态工作进程——默认为物理核心数的一半；只有当交互式工作发现所有工作进程都在忙时，工作进程池才会超出这一数量扩容，直至其上限。检测到前台活动（有用户请求正在处理、且处理时间尚未超过一分钟，或最近十秒内有过用户请求）时，后台工作最多只运行一个任务：各个编译共享处理器的功耗预算，每多一个后台编译，都会拖慢用户自己的编译。当前台活动恢复时，工作进程资源会被快速收回——运行中的低优先级任务到达协作式取消检查点后会自行重新入队，若超时则以强制终止进程作为兜底——因此突发的连续输入绝不会被大量索引构建阻塞。任务如果十秒内都不理会取消、因而被终止，就按丢失的工作处理，重试次数有上限。

**按内存准入**：无状态工作运行期间，主进程每秒采样一次机器剩余的内存，以及每个工作进程自身占用的内存。剩余内存在 Linux 上取可用内存与 clice 所在的各个内存 cgroup 仍能容纳的量中的最小值，其中没有任何进程映射的文件缓存计为空闲；在 macOS 上是物理内存减去系统其余部分占用的内存，压缩页计算在内，作为可复用页面交还的页面则不计在内；在 Windows 上取可用物理内存与剩余提交额度（commit charge）中的较小值。有一部分预留内存始终保持空闲：内存总量的 5%，至少 512 MiB——macOS 上为 10%，至少 1.5 GiB，因为它的内存压缩器早在内存耗尽之前就会拖慢一切。只有当剩余内存减去正在运行的后台任务接下来还会增长的部分后，仍能容下新任务的预期峰值和预留内存时，后台任务才会启动。文件的预期峰值是它上次被索引时其工作进程达到的内存峰值，这一数值保存在索引中；从未被索引过的文件，预期峰值取迄今观测到的各次峰值的第 75 百分位数：已知的峰值不足三个时至少为 1.5 GiB；同时运行的这类任务超过三个时，第三个之后的每一个也至少为 1.5 GiB，因为估计有误只有在任务的内存超出估计时才会显现，而任务每次只会被终止一个。在 macOS 上，工作进程自身的内存取的是它的 footprint（系统统计的进程内存占用）：分配器复用的页面，只有在分配器告知系统时才会计入 footprint——clice 在 macOS 上使用的分配器 mimalloc 会告知，系统自带的分配器则不会。放不下的任务会让排在它后面、放得下的任务先运行，最多持续半分钟；此后队列会停下来等它。没有后台任务在运行时，排在队首的任务只要剩余内存还容得下预留内存就会启动：等待也不会释放任何内存。

**内存紧张时**：当剩余内存低于预留内存，或者按后台任务的增长速度推算（每个任务最多增长到其预期峰值），两秒内就会低于预留内存时，最新启动的后台任务会被终止：它损失的工作最少，往后的增长却最多。在 Linux 上，有多个后台任务运行时，一旦系统开始把 clice 工作进程的内存换出到交换空间，无论可用内存显示多少，也视为内存不足：系统可能保留大量文件缓存，转而使用交换空间。没有任何其他工作（包括已打开文档上的工作）时单独运行的后台任务，可以动用预留内存，直到按同样方式推算只剩三分之一时才会被终止；超出最小数量的空闲工作进程会先退出，为它腾出空间。每次只终止一个任务，等前一个工作进程确实退出后才会终止下一个。前台工作绝不会因为内存而被推迟或终止。与其他工作一起运行时被终止的索引任务，会把它达到的内存记为预期峰值的下限，并在下一轮重新运行，不占用它的重试次数。没有其他工作在运行时仍被终止的任务，说明这台机器容纳不下它：在文件发生变化之前不会再运行，`clice index` 会把它与失败项分开列出，并附上它达到的内存。工作进程内存分配失败也按同样的方式处理，绝不会被当作其文件导致的崩溃。其他工作（PCH 或模块构建）如果其工作进程耗尽了内存，会再发送一次。

## 崩溃恢复

进程隔离的核心价值在于崩溃恢复——把单个工作进程的故障限制在该进程内，不影响整体服务。

### 崩溃由谁引起

一个工作进程会同时运行多个请求——有状态工作进程会并行地为多个文档编译和响应查询——因此仅凭它的退出，无法判断是哪个请求导致了崩溃。为此，即将退出的工作进程会在 stderr 的最后一行写明它当时正在运行的请求：崩溃处理程序运行在出错的线程上，而该线程知道自己在处理哪个请求。主进程先读取这一行，再答复随该工作进程一同终止的请求：

- 工作进程写明的请求就是崩溃的起因，这类工作的崩溃归咎于该请求的文档。
- 其他正在进行的请求只是受到牵连。它们会重发一次，其文档不会被归咎。
- 如果退出时没有写明任何请求——工作进程被 OOM killer 或信号从外部终止，或者在无法报告的位置崩溃——所有正在进行的请求都会重发一次。某个请求如果以这种方式终止了两次，且两次都是所在工作进程上唯一的请求，就会被归咎；如果当时有多个请求正在进行，就无从得知是哪一个导致的，因此一个都不归咎。

### 崩溃文档的表现

归咎按文档、按工作类型记录：编译、预编译 Preamble、文档导入的模块、各项查询（悬停、语义高亮、内联提示、文档符号、折叠范围、代码操作、文档链接）、代码补全、签名帮助和格式化。一次崩溃只会暂停该文档的这一类工作：

- 编译或 Preamble 崩溃后，文档没有 AST。它的诊断让位于文件第一行上的一条警告，警告写明崩溃的是什么以及工作进程如何终止；需要 AST 的功能返回空结果。代码补全和签名帮助也随之暂停，因为它们解析的是同一份代码。
- 查询崩溃只暂停该查询；编译产生的诊断保留，并附加这条警告。
- 模块构建崩溃后，所有导入该模块的文档都得不到它；这些文档仍会编译，报告模块缺失，并带有这条警告。
- 多个文档共享的 Preamble 只崩溃一次：其他文档会显示这条警告，而无需各自再崩溃一次。
- 读取预编译 Preamble 时崩溃的编译会先重建 Preamble，因为损坏的缓存文件也会以同样的方式崩溃：损坏的文件不带警告地自行恢复，只有在重建后的 Preamble 上再次崩溃才归咎于该文档。
- 正在等待工作进程的请求，如果有一个同类请求在相同内容上崩溃，就不会再发出：它返回空结果，而不是让工作进程再崩溃一次。

工作进程无法处理的请求返回空结果，而不是错误；文件上的警告会说明缺失的原因。暂停属于文档，而不属于为它提供服务的项目：文档转到另一个项目时（例如它的上下文被切换到那个项目中的某个文件），暂停仍会保留。

### 何时重试

文档保持不变时，被暂停的工作绝不会重试：再次发出请求不会再次让工作进程崩溃。只有在以下情况下才会重试：

- 文档或它包含的文件发生变化后重试，但须距崩溃已过去两秒，且最多容许连续崩溃三次——输入到一半时导致崩溃的代码，通常在写完整后就不再崩溃；
- 保存文档时立即重试。保存就是显式的重试，并会重新开始计算这三次。

编辑后紧接着发生的第一次崩溃不会显示警告，因为它很可能来自输入到一半的代码，而下一次编辑就会重试。关闭再重新打开文档会重试被暂停的工作：重新打开的文档不带任何暂停。被暂停的工作一旦返回结果，暂停及其警告随即清除。

后台索引遵循同样的规则，但不显示警告：如果某个文件自身的索引运行导致工作进程崩溃，该文件会被跳过，直到它发生变化。索引运行若在读取其目标的构建所声明的预编译头文件时崩溃，会不带它再运行一次，由该文件自行解析这个头文件。如果这次运行成功，崩溃就记在该预编译头文件上，就像编译在读取 Preamble 时崩溃一样：损坏的预编译头文件会在处理下一个文件前重建；一再让读取它的运行崩溃的，则会暂时弃用一段时间。如果再次崩溃，这次崩溃就算该文件自己的。

构建声明的预编译头文件如果让构建它的工作进程崩溃，在该头文件发生变化之前不会再次构建；在此期间，读取它的文件自行解析该头文件。

模块若因代码中的错误而构建失败，只要它读取过或查找过的文件都没有变化，就不会重建：导入它的文档在没有它的情况下编译，并报告这些错误。一旦其中某个文件发生变化，或者编译参数发生变化，它就会重建；每次保存导入它的文档时，它也会重建。

预编译 Preamble 即使代码中有错误也照常构建，使用它的文档会把这些错误连同自身的错误一起报告。一旦它读取过或查找过的某个文件发生变化，这样的 Preamble 就会重建；每次保存使用它的文档时，它也会重建。

### 工作进程重启

1. 主进程检测到进程退出，立即从路由表中移除已终止工作进程的文档，并启动替代进程——偶发崩溃时立即启动，循环崩溃时采用指数退避
2. 找不到对应类型存活工作进程的请求会等待其恢复，而不是直接失败；在此期间，文档保留当前显示的诊断
3. 有状态工作进程上的文档会在下一次请求时重新编译——用户可能会感受到短暂延迟，但不会丢失任何编辑内容：文本缓冲区保存在主进程的 Session 中

### 崩溃预算与恢复

每个工作进程槽位都有崩溃预算，并在两次重启之间采用指数退避。只有没有写明任何请求的退出才会计入预算，但其中会话被终止（SIGTERM、SIGINT 或 SIGHUP）以及空闲工作进程（既没有运行请求、也没有持有文档）被 SIGKILL 这两种情况除外：由请求导致的崩溃归咎于该请求的文档，而文档的暂停已经将其控制住；空闲的工作进程被 OOM killer 或用户终止，说明不了工作进程能否保持运行。正在运行请求或持有文档时被终止的工作进程则会计入预算：如果当时有多个请求正在进行，或者一个请求也没有，就不会归咎于任何请求，只有预算能让一再被终止的负载慢下来。某个请求若被查明两次都是单独随工作进程终止的，最终仍会被归咎，这两次退出计入的预算也随之退还。持续正常运行一段时间后，预算会重置，因此偶发崩溃不会累积到让槽位彻底停用。耗尽预算的槽位会停止重启——但并非永久停止：冷却期结束后，其预算会恢复，槽位也可以按需重新启用。因此，在系统性故障期间，工作进程池会暂时降级（工作进程更少、后台索引变慢），并在诱因消失后自行恢复，整个过程中主进程始终不会中断。

### 卡死与超大结果

请求运行超过时限，会被视为工作进程卡死：该工作进程会被终止，请求则像崩溃一样被归咎，显示同样的警告，也遵循同样的重试规则。构建（编译、PCH 或模块构建、索引运行）的时限为十分钟，其他请求为两分钟。无状态工作进程的时限按它的 CPU 时间计算，因此机器负载很高时，构建只会变慢，而不会被终止；无状态工作进程的 CPU 时间如果五分钟没有增长，同样视为卡死。已打开文档上的工作则从同一文档之前的请求结束时开始计时，因为它的工作进程会逐个运行这些请求；查询所在的工作进程上有构建在运行时，查询不计时，因为它可能要排在构建后面等待线程，但这段不计时的时间最长不超过构建的时限。一次终止会把该工作进程上每个超过时限的请求都列为起因。超出进程间消息 64 MiB 上限的索引会改由缓存存储中的文件传递。没有缓存存储时，这样的索引就无法发送，但这不算崩溃：已打开文档的编译会保留其诊断，只丢弃该文档自身的索引，并显示一条警告；该文件的后台索引运行则会一直失败，直到文件发生变化。

## 设计决策与权衡

**为什么选择多进程而不是多线程？** 线程无法隔离崩溃——一个线程的段错误会终止整个进程。线程也无法隔离内存泄漏——所有线程共享同一个地址空间。多进程增加了 IPC 开销（bincode 序列化/反序列化），但提供了真正的故障隔离。对于 Clang 这样已知存在大量可能导致崩溃和内存泄漏的执行路径的库，进程隔离是工程上的必要选择。

**为什么要分设有状态和无状态工作进程，而不是采用统一的工作进程池？** 两者的调度策略根本不同。有状态工作进程需要文件亲和性（确保 AST 复用）；无状态工作进程需要负载均衡和优先级队列。统一的工作进程池要么牺牲亲和性（导致频繁重编译），要么牺牲调度灵活性（无法区分优先级）。将两者分开，可以让每种工作进程专注于各自的调度需求。

**为什么主进程是单线程的？** 主进程的工作量很轻——它只做路由和状态管理，不做编译。单线程避免了所有并发控制的复杂性（锁、原子操作、竞态条件），而基于协程的事件循环足以应对 I/O 密集的路由工作。

## 已知限制

- **前台工作没有内存上限。** 后台工作会在预留内存耗尽之前被终止，但已打开文档编译的某个有问题的翻译单元，可能让它的工作进程内存占用不断增长，直到操作系统的 OOM killer 介入。持有请求或文档的工作进程在 OOM killer 的排序中仅略高于主进程，因此会先于会话被终止；空闲的工作进程则保持与主进程相同的分值，因为终止它并不能释放任何内存。被终止工作进程上的请求按“退出时没有写明任何请求”的规则处理。

- **内存上限过小会让后台工作停滞。** 剩余内存一直低于预留内存（至少 512 MiB，macOS 上为 1.5 GiB）时，任何后台任务都不会启动：内存上限只比这略高一点的容器永远不会建立索引；在被其他程序占满内存的机器上，后台工作会一直等到它们把内存还回来。

- **同步启动。** 服务器在开始响应请求之前，会先完成编译数据库加载、工具链缓存预热和初始依赖扫描，而且目前还没有进度报告——在超大型项目中，服务器启动后的一段时间内可能看起来像无响应。
