# 编译任务图与模块编译

## 背景

C++20 引入了模块，改变了 C++ 自诞生以来一直使用的独立编译模型。传统 C++ 中，每个源文件独立编译为目标文件，文件之间通过头文件共享声明。模块打破了这种独立性：

```cpp
// math.cppm — module interface unit
export module math;
export int add(int a, int b) { return a + b; }

// main.cpp — imports the module
import math;
int main() { return add(1, 2); }
```

编译 `main.cpp` 之前，必须先编译模块接口单元 `math.cppm`，产出预编译模块文件（PCM）。如果项目中有多层模块依赖——A 导入 B，B 导入 C——编译顺序必须是 C → B → A。这构成了一个有向无环图（DAG），节点是模块文件，边是 `import` 关系。

构建系统（CMake、Ninja 等）天然适合处理这种 DAG 调度：扫描所有文件、构建完整依赖图、按拓扑序编译。但 language server 面临的挑战不同：

**实时性。** 用户打开一个导入了模块的文件后，期望在数百毫秒内获得编辑反馈。等待整个模块图编译完成是不可接受的。language server 需要一种惰性的、按需的编译策略——只编译当前文件实际需要的那些模块。

**文件变更的级联影响。** 当用户修改一个模块接口文件并保存时，所有直接或间接依赖它的模块的 PCM 都已过时。language server 需要检测这种情况，取消正在进行的编译，标记受影响的模块为脏，在下次需要时重新编译。

**并发与取消。** 多个文件可能同时需要同一个模块的 PCM。language server 需要避免重复编译，让后到达的请求等待先发起的编译完成。同时，当用户关闭了触发编译的文件、不再需要某个模块时，正在进行的编译应该能被取消以释放资源。

**临时的循环依赖。** 虽然 C++ 模块不允许循环 `import`，但用户在编辑过程中可能临时引入循环。language server 需要检测并报错，而不是死锁。

在 clangd 中，C++20 模块支持长期处于实验阶段，缺乏专门的设计。[clangd/clangd#1293](https://github.com/clangd/clangd/issues/1293) 是 clangd 团队对模块支持问题的总结——结论是“这些不是能够修复的 bug，需要全新的设计和基础设施”，并且当时“没有人有计划或时间来做这件事”。多年后，相关问题持续出现：[clangd/clangd#2569](https://github.com/clangd/clangd/issues/2569) 列举了模块中缺失的关键功能（重命名、查找引用等）；[clangd/clangd#2292](https://github.com/clangd/clangd/issues/2292) 和 [clangd/clangd#2497](https://github.com/clangd/clangd/issues/2497) 反映了 clangd 与构建系统共用 PCM 文件导致的文件锁定冲突——clangd 打开 PCM 文件后，构建系统无法覆写更新。

这些问题的共同根源是缺乏一个为 language server 场景专门设计的编译调度系统。clice 通过一个通用的**编译任务图**来解决：每一个昂贵的构建产物——模块 PCM、preamble PCH、文档 AST、一次性批量运行——都是同一个图中的节点，具备惰性构建、按需编译、实时协作取消和依赖级联。模块是这个图最丰富的使用者，本页以它们作为贯穿示例。

## 设计

### 一个图，多个节点族

任务图本身刻意保持很薄：它只知道节点、边、interest、轮次和失效——而不知道节点构建什么。节点的具体*含义*由其**族**定义：

- **PCM 族**：每个模块一个节点，边是 `import` 关系。所有模块相关策略都在这里。
- **PCH 族**：每个 preamble 内容键一个节点——preamble 相同的文件共享一个节点和一次构建。
- **AST 族**：每个打开的文档一个节点，产出发布的 feature 结果。
- **TU-run 族**：后台索引和批量 lint 共享的一次性 translation unit 运行。

本节剩余部分描述图的通用契约；模块相关行为会明确说明。

### 惰性构建

与构建系统在编译前扫描所有文件并构建完整 DAG 不同，编译任务图是惰性构建的——节点只在编译请求第一次到达它时才创建，而它的每一轮构建都会重新解析自己的依赖。当用户打开一个文件时，只有该文件实际需要的模块链被扫描和编译，而不是整个项目的模块图。

有两个模块入口点：

- **编译模块**：编译指定模块及其所有传递依赖，产出 PCM 文件。用于模块接口单元自身。
- **编译依赖**：编译指定文件的所有模块依赖，但不编译文件本身。用于普通源文件——它们不属于模块 DAG，但可能通过 `import` 使用模块。

无法解析提供者的 `import` 不会让图失败：它变成一个 **placeholder node**（占位节点），从不运行，只被依赖。当提供者稍后出现——文件被创建，或编译数据库重新加载发现它——图会更新边并使依赖方失效，这些依赖方随后针对真实模块重新构建。

### 引用计数

引用计数是编译任务图的核心调度机制，追踪“当前有多少活跃请求关心某个节点”。它回答两个问题：是否需要启动编译？是否可以取消编译？

当请求需要某个节点时，节点的引用被获取；当请求完成或被取消时，引用被释放。引用降到零意味着当前没有任何活跃请求关心这个产物。

引用计数在两个层级上运作：请求级和依赖级。请求级引用表示“该请求正在等待产物”；依赖级引用表示“该节点的构建正在等待其直接依赖完成”。后者确保当另一个模块的构建依赖某个模块时，即使原始请求已被取消，该模块也不会被过早取消。

### 编译轮次

每次构建尝试构成一个轮次。针对同一节点的并发请求加入正在运行的轮次，而不是各自发起新的轮次；等待者通过轮次结果得知完成并决定下一步动作。一个轮次有三种可能的结果：

- **成功**：产物构建完成，脏标志清除。
- **失败**：编译错误（依赖失败、循环依赖检测等），脏标志保留。
- **过时**：轮次被取代（编译期间文件被修改，或引用计数降为零），等待者自动驱动新一轮。

失败不是粘性的——保留脏标志意味着用户修复错误后，下一次请求会自然触发重试，无需重启服务器。

### 协作式取消

取消是建议性的，从不破坏性终止。引用计数降到零（或轮次被取代）会设置停止标志；正在运行的构建在编译内部的声明级检查点观察到该标志后提前收尾，轮次向等待者发布真实结果。正在运行的轮次绝不会在执行中途被拆除——这意味着构建结束时的提交序列（先写产物，再注册其元数据）一旦开始就会执行完毕，因此取消绝不会留下半注册的产物。

### 脏状态与世代计数器

每个节点使用脏标志表示需要重新构建。世代计数器是一个单调递增的值，在每次文件更新时递增，用于检测异步竞态：构建在启动时记录当前世代，完成时比较——不一致意味着文件在编译期间被修改，结果为过时。

### 依赖关系

模块节点维护正向依赖（它们导入的模块）和反向依赖（导入它们的模块）。正向依赖通过惰性解析获得；反向依赖在解析时回填。反向依赖是文件变更时级联通知的基础——从被修改的模块出发，沿反向边可以找到所有受影响的模块。

模块名到文件的映射由 DependencyGraph 维护（见[依赖扫描](dependency-scanning.md)）——启动时的快速扫描发现所有模块声明，建立模块名 → 文件路径的注册表。PCM 节点族使用该注册表将 `import` 语句解析为具体文件路径。

## 实现

### 编译流程

模块编译请求的完整流程：

```
Request enters
  │
  ├─ Acquire interest on the target module's node
  │
  ├─ Target not dirty? ──→ Return immediately (PCM available)
  │
  ├─ No round in progress? ──→ Start a build round
  │                             │
  │                             ├─ Lazily resolve dependencies (scan import declarations)
  │                             ├─ Check for self-cycle
  │                             ├─ Acquire interest on direct dependencies
  │                             ├─ Wait for each dependency to compile
  │                             ├─ Dispatch to worker process (produce PCM)
  │                             └─ Check generation counter ──→ Mismatch = Stale
  │
  ├─ Join the round and wait for its outcome
  │
  └─ Based on result: Success → return / Failed → error / Stale → retry
```

惰性解析使用 Clang 预处理器进行精确扫描，与启动阶段依赖扫描使用的快速词法扫描不同。快速扫描不展开宏或计算条件编译，适合构建全局的包含关系概览；精确扫描展开所有预处理指令，得到该文件在当前编译命令下实际的模块依赖。解析在每一轮构建开始时都会重新执行，而不是缓存起来，因此编译命令或 import 列表的变化总能被下一轮看到。

> 模块实现单元（带有 `module X;` 但没有 `export`）隐式依赖对应的模块接口单元。精确扫描检测这种情况并自动添加依赖。

### 延迟零引用取消

当引用计数降为零时，不会立即请求取消；检查被短暂推迟——如果那时引用计数仍为零，协作式取消继续执行。

这处理编译请求被取代的场景。当用户在编译期间编辑，新请求替换旧请求：旧请求释放引用（瞬间归零），随后新请求重新建立引用。立即取消会不必要地终止共享依赖的构建；延迟检查让这种交接顺利完成。

### 级联更新

当模块文件被保存（didSave）时，图执行级联更新：

1. 把被保存文件的节点标记为脏，递增其世代计数器，并取代正在进行的轮次
2. 沿反向边遍历所有传递依赖方——既包括早先轮次记录下的持久边，也包括仍在进行的轮次的候选边；对每个受影响的模块：取代其运行中的轮次、标记为脏、递增世代
3. 使受影响的缓存 PCM 失效，避免任何请求消费过时产物

正向边保持不动：被保存文件的下一轮会重新扫描它的 `import` 声明并替换这些边，因此编辑中删掉的 import 要等这次重扫之后才停止级联。级联更新不修改引用计数——现有等待者保留自己的引用。观察到 Stale 结果后，它们会自动驱动新一轮。

### 循环依赖检测

在等待某依赖编译完成之前，图会检查等待环：从目标节点出发，沿依赖链搜索，只跟随当前正在构建的节点，检查链是否回到当前等待者。如果检测到环，立即返回失败，避免死锁。

### 结构化并发

所有编译轮次作为任务运行在图拥有的 task group 中，提供结构化并发保证：关闭时停止接收新任务、协作式取消、等待帧展开，确保没有悬空的构建任务残留。已完成的轮次帧在完成时立即回收。

### PCM 缓存

PCM 文件按配置而非内容命名：模块名加上编译器版本、工作目录、源文件路径和前端相关参数的哈希，存储在专用缓存目录中。这与构建系统产物完全隔离，避免文件锁定冲突。内容变化由下文的依赖快照捕获，而不是靠文件名。

缓存 PCM 通过依赖快照校验：每个依赖的身份和观测到的内容版本与共享文件表比对（stat 快速路径，内容哈希确认——见 [Incremental Compilation](incremental-parse.md)）。只有当依赖内容实际变化时才重新编译，避免“仅 touch 未修改”导致的不必要重建。缓存元数据与索引一起持久化，服务器重启时恢复；Clang 自身的 PCM 校验作为最后兜底。

### 与编译流程的集成

在分发文档 AST 或交互式构建之前，其依赖准备会获取所需的 PCM 节点——这是编译准备的第一步，在 PCH 构建之前执行。import 扫描基于请求的实际缓冲区文本运行（包括为头文件上下文合成的后缀），因此用户已输入但尚未保存的 `import m;`，其 PCM 会在解析需要之前被构建。

## FAQ

- **为什么用引用计数而不是任务队列？** 任务队列无法表达“这个编译不再被任何人需要”。当用户关闭触发编译的文件时，继续编译浪费资源。引用计数精确追踪需求，使取消决策有据可依——不是基于超时或启发式判断，而是基于当前是否还有请求在等待结果。

- **为什么延迟零引用取消而不是立即取消？** 在事件循环模型中，一个操作的多个步骤在同一 tick 内完成。当编译请求被取代时，旧引用释放、新引用随后建立，中间存在瞬间的零引用。立即取消会不必要地终止共享依赖——延迟检查确保引用交接不触发取消。

- **为什么用协作式取消而不是销毁构建任务？** 在构建中途销毁协程帧会让每个 await 点都可能成为退出点，而且构建末尾的提交序列（写入产物、注册元数据）绝不能被打断成两半。建议式停止标志让构建在明确的检查点退出，并且总能发布真实结果，代价是取消略有延迟。

- **为什么用世代计数器而不是锁？** master 进程是单线程事件循环，没有数据竞争。需要检测的“竞态”来自异步时序——“编译期间文件是否被更新过”。世代计数器以最小开销回答这个问题，不需要引入锁。

- **为什么惰性解析依赖？** 依赖解析需要对每个模块文件运行 Clang 预处理器（精确扫描），成本不低。如果启动时解析所有模块依赖，会增加启动时间。惰性解析确保只扫描实际需要编译的模块——打开一个文件不会触发扫描整个模块图。

- **失败为什么不是粘性的？** 用户正在编辑代码，语法错误是常态。如果把失败标记为持久状态，用户修复错误后不重启服务器就无法获得正确结果。保留脏标志让下次请求自然触发重试。

- **为什么把 PCM 存储在独立的缓存目录？** clangd 与构建系统共用 PCM 文件，会导致文件锁定冲突——language server 打开 PCM 后阻止构建系统覆写更新（见 [clangd/clangd#2292](https://github.com/clangd/clangd/issues/2292)）。clice 把 PCM 放在自己的缓存目录里，避免这个问题。代价是额外的磁盘空间占用和首次编译的额外时间。

## 已知局限

- **依赖解析的确定性。** 解析依赖和实际编译之间存在时间窗口。如果文件在此期间被修改，解析出的依赖可能与编译时的实际依赖不一致。世代计数器会检测到这种情况并触发重试，但代价是额外的编译开销。

- **全新的模块提供方。** 一个 `import` 的提供模块从未保存到磁盘时无法构建——没有文件可编译。一旦提供方被保存，会通过占位节点机制被发现；之前无法解析的 import 链会在其依赖方下次编辑或重新打开时恢复，而不是自发恢复。

- **图状态在内存中。** 节点和边的状态不会在服务器重启后保留；图在下次运行时根据持久化缓存和依赖注册表惰性重建。
