# Toolchain Changelog

Pitfalls met while building and consuming the prebuilt LLVM packages: the package
definition (`scripts/build-llvm.py`, `build-llvm.yml`, the clice-llvm patches) and
the consumer side (`cmake/llvm.cmake`). `llvm-changelog.md` covers clang API changes;
this file covers everything around them. Every entry: what you see, why, what we do,
how to check it before spending CI time. Append to it with every toolchain change.

## 2026-09: package redefinition, clang and LLVM 23.1.1 together

The package is now built from an explicit component list with no code-generation
target, carries line-table debug info only, keeps assertions on outside the LTO
variant, ships the Debug variant as static archives, and records its configuration
in a manifest that `cmake/llvm.cmake` checks. The pixi clang and the packaged LLVM
move together (both 23.1.1); the rule from here on is that they are always the
same release.

### CI mechanics

- `gh workflow run build-llvm.yml` needs `--ref <branch>` to use the branch's script and workflow; without it the dispatch runs `main`'s.
- A new dispatch on the same branch cancels the run in progress (`concurrency: build-llvm-${{ github.ref }}`); `gh run cancel` sometimes needs a retry when the API times out.
- `gh run view --job <id> --log` refuses while the run is still in progress; `gh api repos/clice-io/clice/actions/jobs/<id>/logs` works for a finished job of a running run.
- The script `os.chdir`s into the LLVM tree; every path argument is resolved before that. A relative `--build-dir` is relative to the LLVM tree (the workflow passes `build`).
- 23.1.1 first round (run 35451776978), all 14 legs green: Linux RelWithDebInfo 38 / LTO 48 / Debug-ASan 66 min, macOS 34–47 min, aarch64 Linux cross 50–54 min, Windows aarch64 cross 69 / 82 min (build step 61 / 50 min), Windows x86_64 native 119 / 106 min for the build step alone with the same 2207 compiles as the cross legs. Archives (MB, new / old): Linux x86_64 releasedbg 102 / 302, lto 199 / 686, debug-asan 164 / 971; aarch64 Linux 100 / 299, lto 200 / 687; macOS aarch64 129 / 859, lto 212 / 1727, debug-asan 196 / 146 (static archives replace 598 dylibs); macOS x86_64 134 / 889, lto 210 / 1755; Windows barely moved (261 / 263, 594 / 636, 245 / 250, 589 / 625) because of the `-Zi` override above, and the old Windows packages also carried `bin/LTO.dll` + `bin/Remarks.dll` (126 MB) that `LLVM_BUILD_TOOLS=OFF` did not stop; the new ones have no `bin/`.
- Windows legs are slow for a reason that is now measured: one Support TU (`CommandLine.cpp`, clang-cl 23.1.1, the CI flags) takes 4.2 s with line tables and 14.3 s with `-Zi` full CodeView, so the `-Zi` override above cost the first 23.1.1 round about 3x per compile (native legs 106–119 min for the build step). A cold ccache adds 10% (x86) to 30% (aarch64) per compile, not worth removing. The aarch64 target compiles 2.3x _slower_ than x86 locally (9.9 s), yet in CI the aarch64 cross legs finished in half the time of the native ones with the same TUs; the same Linux leg took 38 min in one round and 60 in the next, so runner variance is large. The `Runner info` step in `build-llvm.yml` records cores and CPU model per leg for the next comparison.
- 23.1.1 second round (run 35459225084, the `-Zi` and manifest fixes): all 14 legs green; Windows archives halved (x86_64 releasedbg 133 MB, lto 217; aarch64 127, lto 212) and the Windows packaging step dropped from 6–19 to 2–3 min, but the Windows build step did not move (native releasedbg 114 min, lto 102; aarch64 cross lto 96 against 50 in the round before, releasedbg 58): on the GitHub Windows runners compile time does not track the amount of debug info, and the same job varies almost 2x between rounds.
- Windows runner speed, settled by an A/B on a scratch branch (Windows-only matrix, `Set-MpPreference -DisableRealtimeMonitoring` on or off, 4 legs each, a `Runner info` step printing the CPU): build-step minutes with Defender on 86 / 93 / 65 / 114, off 102 / 94 / 86 / 117. Defender makes no difference; the spread is the CPU the `windows-2022` label happens to hand out (AMD EPYC 9V74 and Intel Xeon 6973P fast, EPYC 7763 and Xeon 8370C slow, all 4 cores). Nothing on the runner is worth tuning; faster Windows legs mean a larger or self-labelled runner, or cross-compiling the msvc target from Linux.
- Baselines from the libc++ attempt below, same component list and targets: a full leg (RelWithDebInfo, LTO) took 52 minutes on macOS and on the aarch64 Linux cross build, against 130–226 minutes for the old packages; archives 197 MB (aarch64 Linux) and 202 MB (x86_64 macOS) against 687 MB and 1755 MB. The 22.1.8 plan had 2857 build steps / 2207 compiles against 5804 / 4457; the 23.1.1 plan has 2996 / 2307 (Windows 2997).

## 2026-09: libc++ inside the package

The package carries a static, hermetic libc++ (libc++abi merged in outside Windows)
built from the same llvm-project tree by a runtimes pass ahead of the LLVM pass, and
every platform links clice against it: `-nostdinc++ -isystem <prefix>/include/c++/v1`
for the compile, the archive named outright after the objects (`-nostdlib++` plus
`<prefix>/lib/libc++.a`; Windows: `libc++.lib` as a linker input, then
`/DEFAULTLIB:libcpmt.lib`) for the link, hardening `debug`/`fast`/`none` by variant,
the ASan variant linking an uninstrumented libc++. A first attempt (branch
`build/toolchain-23-libcxx`, LLVM 22.1.8 with libc++ 23.1.1) was parked because two
releases in one package cost one workaround per platform; the rows below are what it
found and what the same-release round re-verified. No libc++ patch is carried: the
Windows wide-printf mode is handled with compile flags, and the libc++ is not
sanitizer-instrumented, which retires the Apple lookup patch (both are still on the
clice-llvm branch `patches/22.1.8-libcxx-legacy-wide`).
